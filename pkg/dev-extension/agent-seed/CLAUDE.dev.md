# How this environment differs from the harness

{{#if leased}}**This is a leased workspace, and it runs nothing.** The checkout, the artifacts and the
command-line tools are here; a dev server, a browser, a Firefox, a storybook and a Rancher are
*tools* you attach while you need them and release when you are done - `tools`, `tools start
dev-server`, `tools stop dev-server`. `.claude/rules/tools.md` is the whole of it, and it overrides the
bullets below wherever they disagree: there is no dev server on `localhost:8005` in this pod,
there is no Chromium container beside you (the browser is shared, and `tools start browser`
gives you a session of your own on it), and `dev-server ...` still works because it hands every
verb to `tools`. Release what you attached before you write your summary.

{{/if}}
This is a Kubernetes workspace made by the dev extension, not a harness project container. The skills, rules and prompts above are the harness's, unchanged; only the machinery around them is different. `.claude/rules/environment.md` is the full account and replaces `sidecars.md` and `project-environment.md`, which are not here. The short version:

- **Where things are**: this workspace's tree is `/workspaces/<workspace>` - the node's `dev-workspaces` directory is mounted at `/workspaces` in the workspace's own pod *and* in the agent pod your conversation runs in, at the same path on purpose, so a path means the same file whichever half reads it. It is **not** `/workspace`: that path used to be this tree and is now the agent pod's own directory (its conversations, its home), so `/workspace/artifacts` is a real directory that is not yours and writing there loses the evidence silently instead of failing. `/workspaces/.shared`, `/workspaces/.store` and `/workspaces/.artifacts` are the node's, shared by every workspace on it.
- **Code**: `/workspaces/<workspace>/dashboard` is the checkout (`origin` = your fork, `upstream` = rancher/dashboard). Its dev server is already running at `https://localhost:8005` and reloads on edit. `dev-server status` says which Rancher it runs against, `dev-server --api URL` points it at another one (it restarts and compiles again, 1-3 minutes), `dev-server logs` shows its output and `dev-server restart` restarts it. **Never start a second dev server**, on any port: two webpacks exceed the pod's memory, the container is OOM-killed under both, and every command you were running in it dies with it - and the pod stops its own server while yours runs, so nothing is gained either.
- **The repository is not always rancher/dashboard**: the workspace App has always had a `repo` value and nothing carried it, so every page asked GitHub about rancher/dashboard whatever the workspace was for - a workspace made for another repository's pull request got `GET /repos/rancher/dashboard/pulls/1202 -> 404` and then reported itself "not named for an issue or a PR, so it has no stages". The workspace record carries `repo` now (dev-api reads it off the Installation's values and falls back to rancher/dashboard), and the pages read it. **You can make one for another repository**: `POST $CLAUDE_HARNESS_API/workspaces` takes `repo` as `owner/name` beside `name`, `app` and `cluster`, and a `repo` that is not `owner/name` is a 400 rather than a quiet rancher/dashboard workspace - the spec at `/openapi.json` is the whole shape, and `GET /workspaces` says which repository each one is for. What has *not* caught up is the plumbing under the checkout, so in a workspace for anything else, check rather than assume: the directory is called `dashboard` whatever the repository is; an `upstream` remote pointing at rancher/dashboard is added unconditionally; and the one-time PR checkout fetches `pull/<n>/head` from `upstream`, which for another repository's pull request is the wrong repository. (The node's git mirror holds rancher/dashboard alone, at `/workspaces/.store/git/dashboard.git`; both workspace Apps now attach it only when `repo` ends in `/dashboard`, so another repository is cloned from GitHub rather than given dashboard's history.) Read `git remote -v` and `git log -1` before you believe the tree, fetch the pull request from `origin` yourself, and give `gh` an explicit `-R <owner>/<repo>` rather than letting it guess from a remote.
- **Rancher**: a shared Rancher this workspace points at, not your own sidecar. You are its user through `RANCHER_TOKEN` (no admin password; `RANCHER_ADMIN_USER`/`RANCHER_ADMIN_PASS` are unset), and `node /workspaces/<workspace>/bin/rancher-login.mjs` signs the browser in. Do not change its version, branding or auth provider, and delete what you create in it. **Which URL is it?** Your shell's `$RANCHER_URL`/`$API` come from the workspace's own `.env`, which is written once at setup; the dev server runs against the pod's own `API`, which `dev-server status` shows, and the two can name *different* Ranchers - the one your token is for, and one it gets a **401** or a **404** from. This Rancher may be the parent Rancher in this cluster or a downstream one it manages, and a token for one gets a **401** from the other. So do not assume: verify once, and use the URL that answers `200`:

  ```bash
  WS=/workspaces/<workspace>   # this workspace's root; the checkout is $WS/dashboard
  for U in "$RANCHER_URL" "$API" "$(grep '^RANCHER_URL=' $WS/.env | cut -d= -f2-)"; do
    [ -n "$U" ] && [ "$(curl -sk -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $RANCHER_TOKEN" "$U/v3/users?me=true")" = 200 ] && { echo "use $U"; break; }
  done
  ```

  If that is not the URL `dev-server status` shows, `dev-server --api <that URL>` points the running server at it: that, not a server of your own.
- **Its preferences belong to a person, not to you**: every dashboard you drive - the shared browser and your own dev server alike - is signed in as the person you work for, so Rancher's user preferences (theme, pinned clusters, table views, landing page) are *theirs*. Do not tidy them. The theme is the one that used to leak: the dev extension re-registers it as a cookie of the browser it is loaded in, so switching to light to check a bug now stays with you - but a dashboard without the extension writes it straight to their account, and there the local flip is

  ```js
  document.querySelector('#app').__vue_app__.config.globalProperties.$store.commit('prefs/load', { key: 'theme', value: 'light' })
  ```

  which repaints immediately and is forgotten on reload. Worth knowing either way: `Shift+T` toggles the theme for anybody whose `plugin-developer` preference is set, and the shortcut is only suppressed inside inputs - so a stray keystroke with focus on the page body flips it with nothing to point at.
- **Browser**: Chromium is a container in this pod with CDP on `$CLAUDE_BROWSER_CDP`. `wait-for-sidecars` only waits; nothing needs starting. `browser.mjs` and the recording skills work as in the harness.
- **Firefox**: `tools start firefox` attaches one, for a bug that only happens outside Chromium. It is **not** a second Chromium and **not** CDP: Firefox has had no DevTools Protocol since version 129, so `/json/version` answers 404 and `browser.mjs`, `a11y axtree` and anything else built on CDP will not drive it. It speaks **WebDriver BiDi**, and the endpoint is the session - connect a websocket to the `bidi` address `tools` prints for it, then:

  ```
  session.new  {"capabilities": {"alwaysMatch": {"acceptInsecureCerts": true}}}
  browsingContext.getTree {}                    -> contexts[0].context
  browsingContext.navigate {"context": ..., "url": ..., "wait": "complete"}
  script.evaluate {"expression": "document.title", "target": {"context": ...}}
  browsingContext.captureScreenshot {"context": ...}    -> base64 PNG
  session.end {}
  ```

  **One session at a time.** A second `session.new` is refused with "Maximum number of active sessions", and a client that disconnects without ending its session holds the browser until the pod restarts - so always `session.end`, and if you inherit a locked one, `tools stop firefox` then `tools start firefox` replaces the pod, which is the reliable reset. `data:` URLs are refused by this build; navigate to a real URL. The desktop on its `http` address is what a person watches, so a screenshot taken there is what they will compare against.
- **Harness API**: `$CLAUDE_HARNESS_API` (= `$HARNESS_API`) answers the `/my-work/...` routes with no credential. The sidecar and Jira routes do not exist here.
- **Accessibility**: the whole toolkit works. `a11y axtree` reads Chromium's tree over CDP; `a11y tree`, `say`, `record`, `orca`, `key`, `type`, `screen`, `click` and `shot` run in the browser container, which this one reaches with `kubectl exec -c browser` rather than through a harness API. AT-SPI and speech are installed already; `a11y tier orca` adds Orca and restarts that container.
- **The disk under you is shared with every other workspace on this node**, and three things follow from it. **The package caches are one store**: `YARN_CACHE_FOLDER`, `npm_config_cache` and `CYPRESS_CACHE_FOLDER` all point into `/workspaces/.shared`, so an install here is usually a copy out of a cache somebody else's branch already filled. Leave them where they are - a cache dir of your own re-downloads a gigabyte, and `yarn cache clean` empties the store for all of them. **Installed packages are hardlinked across workspaces**: a sweep runs daily and collapses identical files into one inode, so editing a file under `node_modules` in place edits it in every workspace that has the same version. Patch a dependency the way the ecosystem does - a `resolutions` entry, a patch file, a copy into the repo - never with an editor pointed at `node_modules`. **The command-line tools are one install too**: `bin/gh` and `bin/jq` are symlinks into `/workspaces/.shared/tools`, so replace one by pointing the symlink somewhere else, not by writing over it. Your checkout is yours alone and none of this touches it.
- **Artifacts outlive this workspace**: everything you leave under the workspace's own `artifacts/` (`/workspaces/<workspace>/artifacts`, not `/workspace/artifacts`) - recordings, screenshots, a11y reports, review notes - is kept on the node after the workspace itself is gone, and nothing deletes it but a person choosing to. So it is worth writing for a reader who arrives months later with no pod to ask: name a file for what it shows rather than for the run that made it, and say in the review note what the recording is of.
- **Pending review comments are a file on the disk, not a ConfigMap**: a pull request's unposted review lives under `/workspaces/.artifacts/pr-<n>/review/` on the node - `comments.json` for the comments nobody has posted yet, `run.json` for the review run - and the workspace for that pull request gets it staged as a **symlink** at `artifacts/review/<file>`, chowned to you where the filesystem allows it, so you read and edit it like any file you own. One file under two names, deliberately: it was a `dev-review-pr-<n>` ConfigMap, which put a person's unposted work somewhere they could not see or edit it, and it is kept in the artifact store rather than in the workspace because the state outlives the workspace nearly always - of the sixty pull requests with review state on this node, fifty-four have no workspace left, and nothing deletes `.artifacts` but a person. Three limits. The symlink is made by dev-api when it writes a document and only if a workspace named `...pr-<n>` exists at that moment, so a fresh workspace can have no `artifacts/review` yet. If something that is not that symlink is already in its place - a real file from an older build - it is left exactly as it is and your copy then diverges from the store in silence, so `ls -l` before you trust it. And dev-api writes each document whole, to a temporary name and renamed over the target, so an in-place edit races a post from the Review tab: read it, change it, write the whole document back, or go through `$CLAUDE_HARNESS_API/my-work/pr/<n>/comments` (GET, POST, PUT `/<id>`, DELETE `/<id>`), which is the same two files.
- **The Tools panel is not the list of tools**: it draws Storybook and Rancher and nothing else. The dev server, the shared browser and Firefox came off it because they are what an *agent* attaches - the row said "not running · Attach" at a person who was never going to press it - and not because anything about them changed. All five are still tools, still leased, renewed, released and swept through the same dev-api, and `tools`, `tools start dev-server`, `tools stop dev-server` work exactly as they did. Do not read "the panel has no dev server" as "this workspace has no dev server". The one thing that panel does to a tool you cannot see: when a workspace's stage is waiting on a reviewer or already merged, the page releases the dev server once per visit, because a webpack compiling for somebody who is not coming back is the most expensive idle thing on the node - so a dev server can go away with nobody pressing anything, and `tools start dev-server` brings it back.
- **Shares: two public builds per workspace, and they outlive the lease.** A share is not a tool. Each one is an Installation of the `dashboard-preview` App - `preview-<workspace>` for the dashboard (the panel calls it the Rancher share) and `storybook-<workspace>` for the Storybook - so releasing every tool a workspace holds does not touch it, and it stays up until somebody removes it. One of each, because the name is derived: sharing again replaces what is there. A workspace that has never been shared gets its dashboard share built the first time it is ready without anybody asking, and the workspace's own `.share/auto` records that it happened, so a share you remove stays removed.

  **What is served is a production build, not the dev server**: `yarn build` (or `yarn build-storybook`) of a worktree of the `ref` you name, or of a copy of the working tree as it stands - uncommitted changes included - when you name none. It runs as a Job of its own in the workspace's namespace, `share-build-<kind>`, because the build asks Node for a 4-8 GB heap and doing it in the workspace pod put the container over its limit and took the dev server, the panes and the conversation down with it. While it runs, `/workspaces/<workspace>/.share/<kind>.status` is `building|ok|failed` with the branch and the sha and `.share/<kind>.log` beside it is the build's output; the site itself lands in the workspace's `share/<kind>`. Minutes, not seconds.

  **Where it is served decides how it is routed, which is why moving one is a rebuild.** On a Rancher instance's node it gets an sslip name of its own - `preview-<workspace>.dev-extension.<node ip>.sslip.io` - with a Let's Encrypt certificate, and the dashboard is built to route at `/dashboard/`; with no such Rancher it is served through *this* Rancher's service proxy, behind this Rancher's login, and the dashboard is built to route under that proxy path instead. The two builds are not interchangeable, so a share cannot be moved by editing anything - it is built again. `pickShareHost` makes the choice: a sidebar Rancher of kind `instance` with `phase: 'ready'`, a `clusterId` **and** a `nodeIp` - the starred one when it qualifies, any that does when it does not, and this cluster when none does. The limit worth knowing before you plan around it: an EC2 Rancher made by `rancher-ec2.mjs` has no `clusterId` - nothing registered it as a cluster of this Rancher's - so it is never chosen as a share **host**. It can perfectly well be the Rancher a share **talks to**.

  **Which Rancher it talks to is the cheaper question**: the Rancher is the nginx upstream in front of the build, not something compiled into it, so `retargetPreview` writes the instance's `rancherUrl` and Apps Plus re-renders the nginx; the pod restarts and the build itself is kept. A share may not be pointed at the host it is served on or at the page's own host - nginx would proxy to itself and answer 502 to everything, and the page that did it would be the share - so that is refused with a message rather than attempted.

  **The API**, all of it in `previews.ts`, all of it the extension's: there is no `tools`-style verb for a share inside a workspace, and what a workspace has of its own is the build (the status and the log above). `shareWorkspace(store, workspace, kind, rancherUrl, cluster, host, ref)` builds and puts it up, removing and redeploying when the host it wants is not the host it has. `rebuildPreview(workspace, cluster, kind)` deletes the pods, which is how a rebuilt build reaches a share on another cluster - that pod fetches the build on every start - and `cluster` must be the cluster the share is hosted on, which `previewState` reports as `hostedOn`, not necessarily `local`. `retargetPreview` points it at another Rancher, `removePreview` takes it down, and `previewState` is what everything reads: the link, the certificate, and why it is not up - including the one that reads like a slow build and is not, "The Rancher this was hosted on no longer exists", which means the cluster it was pinned to was rebuilt under it and only sharing again will fix it. A share on another cluster fetches its build through this Rancher's proxy to dev-api with a 30-day token minted when it was made.
- **A Rancher of your own, on one EC2 instance**: `node /seed/rancher-ec2.mjs create <name>` in the agent pod, with `RANCHER_EC2_CREDENTIAL` naming the amazonec2 cloud credential (`cc-5snk6` here - the other one on this account is DigitalOcean, so check before you reach for it). It launches an instance whose user-data installs docker and runs `rancher/rancher` with `--restart=unless-stopped`, finds the newest Ubuntu 24.04 AMI itself, and finds-or-creates a `rancher-ec2` security group with 80 and 443 open and no SSH. `create` prints the bootstrap password once and also keeps it in `dev-rancher-ec2-<name>` in dev-system, which is what `configure` reads later.

  **Two steps, not one.** `create <name>` gets you a box with Rancher on it; `configure <name>` makes it usable, and it does five things over Rancher's own API because there is no sidecar here to do them. It sets `server-url` to the instance's own `<ip>.sslip.io` - the name the certificate is for, not the bare address, or everything it ever provisions gets a TLS error. It finishes the first-time setup: `first-login` false, `eula-agreed`, `telemetry-opt` out, so the person you hand the address to gets a Rancher rather than "it looks like this is your first time visiting", and nobody is asked on your behalf whether this box should phone home. It turns on multi-cluster-management, fleet and rke2. It copies the parent's GitHub login across **with the rancher organisation (`github_org://9343010`) added to the allow-list whatever the parent's is**, because an instance exists to be shown to somebody and an allow-list of one person is a Rancher only its maker can open; it skips GitHub rather than guessing when the parent has no client id or secret to copy, or no principals at all - `accessMode: restricted` with an empty list, on a Rancher where enabling GitHub also stops the local admin being a way in, locks out the person paying for the box. And it copies the cloud credentials the parent marks with `dev.rancher.io/propagate-to-instances`, so the new Rancher can provision something of its own. Each of those is reported by whether it actually took, so read the output rather than assuming. It is idempotent, so running it again is how a half-finished instance is finished. The certificate needs no step: user-data asks the metadata service for the instance's public address and starts Rancher with `--acme-domain <ip>.sslip.io`, so Let's Encrypt issues and renews it and the address opens in a browser with no warning. Rancher answers in three or four minutes; `/ping` returning 200 is the signal.

  **The other verbs.** `list` shows the instances this tool tagged. `sync` rewrites the record the sidebar reads. `orphans` lists every running and pending instance in the account, this tool's (`ours`) and everybody else's (`other`), because the ones that cost money quietly are the ones nothing lists - a node left behind by a deleted Rancher keeps running, keeps its public address, and in one case kept dialling the parent 6,302 times in six hours while `list` could not see it. `delete` takes a **name or an instance id**, and falls back to the untagged ones, which is the only handle an orphan has; it refuses a name that matches more than one instance and tells you the ids rather than terminating the first - this call cannot be undone and the account has other people's boxes in it.

  This is **not** the same thing as an Apps Plus `rancher-single` instance, and the difference matters for what you can do with one. There is no cluster registered with this Rancher, so there is no Fleet target, no `clusterId`, and nothing can be delivered to it the way a workspace share is - `pickShareHost` will not choose it. What it is good for is a real Rancher, at a public address, that nothing else has to keep alive: three moving parts instead of seven, and none of them a tunnel back to this machine.

  The sidebar lists these beside the Apps Plus ones, from `dev-rancher-ec2` in dev-system - a ConfigMap the tool rewrites on every create, delete and sync, because a browser cannot call EC2. If an instance you made is missing from the list, run `sync`; nothing polls AWS on its own.
- **Harvester, and anything else in the SUSE ECM lab**: the lab is on `10.115.0.0/16` and this cluster cannot route to it. The way in is the `lab-vpn` App - OpenVPN in a pod with an HTTP CONNECT proxy in front of it (`apps-vpn.ts`). A pod's routes are its own, so a VPN pod's tunnel is no use to the pod next door; the proxy is what crosses that line, and it runs inside the VPN pod so it has the routes.

  Install it into the workspace that needs it, then reach the lab by setting `HTTPS_PROXY=http://<install>-vpn.<namespace>.svc.cluster.local:8888` - `curl`, `kubectl`, `node` and the dashboard's dev server all read it, so nothing else has to know a VPN exists. **Set `NO_PROXY` with it** (`labProxyEnv` has the list): everything in the cluster and this Rancher's own address must stay direct, or the workspace loses its own API. For a client that cannot be told about a proxy there are four plain TCP forwards on the Service, `:9001` to `:9004`, each pointed at an `<ip>:<port>` in the App's values - by default the three LAB machines reserved for UI development and the ECM Rancher.

  **It will not come up without a profile.** The credentials are a Secret you do not have and must not invent: `lab-vpn-profile` in the workspace's namespace, holding `ca.pem`, `ta.pem` and `auth.txt`. The pod says which of the three is missing and exits rather than retrying a handshake nobody can see failing. If it is absent, say so and stop - do not go looking for a VPN profile on a disk.
- **Publishing**: `gh` is signed in; commit and open draft PRs exactly as the skills say. The person you work for sees uncommitted changes in the workspace's Review tab and the PR in its PR tab.
